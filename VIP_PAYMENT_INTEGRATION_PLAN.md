# VIP+ Payment Integration Plan

## Project status

This document records the provider-neutral design for VIP+ payments in M Launcher Voice.

- Android package: `com.m.launchervoice`
- Firebase project: `m-messenger-9d903`
- VIP membership collection: `vip_members`
- Current Android source is generated by `.github/workflows/blank.yml`.
- Current Firestore rules intentionally prevent Android clients from changing membership status, expiry, payment evidence, or admin roles.
- Payment provider has not been selected. QRIS and bank transfer are the intended payment methods.
- No live payment flow, merchant account, QRIS destination, bank account, or package price is configured yet.

## Required customer experience

1. A signed-in user selects a VIP+ plan.
2. The trusted backend creates a unique payment order using server-controlled plan ID and price.
3. The selected provider returns payment instructions, such as a dynamic QRIS or a bank Virtual Account.
4. The app displays the order and its current status.
5. The provider sends a server-to-server payment notification.
6. The backend verifies the notification using the provider's documented signature/authentication mechanism and, where appropriate, queries the provider API for the authoritative transaction status.
7. The backend processes each successful payment idempotently and activates or extends VIP+.
8. The app refreshes the membership status from Firestore.

A normal static/personal QRIS or ordinary bank transfer cannot reliably activate membership automatically on its own. Automatic activation requires a merchant payment service or bank integration that can provide a verifiable transaction notification/reference.

## Provider-neutral Firestore model (proposed, not deployed)

### `vip_payment_orders/{orderId}`

Suggested server-owned fields:

- `uid`: Firebase Auth UID of the buyer
- `planId`: stable plan identifier (for example `monthly`, `yearly`, `lifetime`)
- `amount`: integer amount in IDR, selected and validated by backend
- `currency`: `IDR`
- `provider`: selected provider identifier
- `providerTransactionId`: provider transaction/reference ID
- `status`: `PENDING`, `PAID`, `EXPIRED`, `FAILED`, or `CANCELLED`
- `createdAt`, `expiresAt`, `paidAt`: server timestamps
- `membershipAppliedAt`: server timestamp after membership update

The Android client must not be allowed to create or update authoritative order fields, mark an order paid, or change a membership record. If client-side order creation is needed, it must call an authenticated backend function; the backend creates the document.

### `vip_members/{uid}`

The backend remains the only authority for membership fields, including:

- `membershipStatus`
- `planId`
- `startedAt`
- `expiresAt`
- `lastPaymentOrderId`

The existing client permissions for profile metadata must remain separate from these protected fields.

## Backend requirements

- Use a trusted server environment such as Firebase Cloud Functions or another secured backend.
- Never put provider secret keys, webhook secrets, or privileged Firebase Admin credentials in the APK, repository, or Android build output.
- Verify webhook authenticity; do not trust a success message sent by the Android app.
- Make webhook processing idempotent so retries cannot grant duplicate membership.
- Match provider transaction ID, order ID, amount, currency, and expected status before granting VIP+.
- Use a Firestore transaction or equivalent atomic operation when marking an order paid and applying membership.
- Define renewal rules before launch (for example, extend from the later of now or the current expiry date).
- Treat lifetime membership separately from expiring plans.
- Log failures without exposing payment secrets or unnecessary personal data.
- Consider Firebase App Check for callable app-to-backend requests.

## Decisions still required

1. Payment provider and merchant account approval.
2. Prices for monthly, yearly, and lifetime plans.
3. Exact benefits included in each VIP+ plan.
4. Renewal, cancellation, refund, and expired-order policies.
5. Backend hosting/billing configuration and deployment permissions.

## Implementation boundary

This file is a design record only. It does not enable payment, create real payment orders, activate VIP+, or change Firestore security rules. Those changes must wait until the provider, prices, and backend configuration are confirmed and tested.
